# 1. Overview

SysY is the source language for the compiler implemented in the compiler technology lab, and it is a subset of the C language. A SysY source file contains exactly one definition of the `main` function. It may also contain global variable declarations, constant declarations, and other function definitions. SysY supports the 32-bit signed integer type `int` and its one-dimensional array type. The `const` qualifier is used to declare constants.

SysY itself does not have built-in language constructs for input/output (I/O). I/O is provided via a runtime library, whose library functions can be invoked inside functions of SysY programs. Some parameters of SysY runtime library functions may fall outside the data types supported by SysY (e.g., string literals). The SysY compiler must handle such cases and correctly pass these arguments from SysY programs to the SysY runtime library.

- **Functions**: Functions may or may not take parameters. Parameter types can be `int` or one-dimensional arrays of `int`. A function may return an `int` value or return nothing (declared as `void`). For `int` parameters, pass-by-value is used. For array-type parameters, the starting address of the array is passed instead. A function body consists of variable declarations and statements.
- **Variable / Constant Declarations**: Multiple variables or constants may be declared in a single declaration statement, optionally with initializers. All variables and constants must be defined before use. Declarations outside functions are global; declarations inside functions are local.
- **Statements**: Statements include assignment statements, expression statements (expressions may be empty), blocks, `if` statements, `for` statements, `break`, `continue`, and `return` statements. A block may contain variable declarations and statements.
- **Expressions**: SysY supports basic arithmetic operators (`+`, `-`, `*`, `/`, `%`), relational operators (`==`, `!=`, `<`, `>`, `<=`, `>=`), and logical operators (`!`, `&&`, `||`). Non-zero values represent true, and zero represents false. Relational or logical operations evaluate to `1` for true and `0` for false. **Operator precedence, associativity, and evaluation rules (including short-circuit evaluation for logical operators) are identical to those in C.**

# 2. Runtime Library

Programs perform I/O via `getint` and `printf`. To test programs in C, simply declare `getint` as shown below:

```
int getint() {
int t;
scanf("%d",&t);
while(getchar()!='\n');
return t;
}
```

The syntax of `printf` is `'printf' '(' <StringConst> {, <Exp>} ')'`. `<StringConst>` denotes a string constant terminal, specified in Section 3 Grammar and Test Coverage Requirements, Subsection 3.5 String Constants. Parsing `<StringConst>` involves types outside SysY’s native type system; the SysY compiler must handle this case.

# 3. Grammar and Test Program Coverage Requirements

## 3.1 Grammar

The grammar of SysY is specified in Extended Backus–Naur Form (EBNF):

- `[...]` denotes an optional item.
- `{...}` denotes an item that may appear zero or more times.
- Terminals are either quoted strings or tokens such as `Ident`, `IntConst`, `StringConst`.
- Quoted strings like `'main'` are reserved keywords.

The start symbol is `CompUnit`.

> 
> Important: Please also refer to the semantic constraints in Section 4.

```
CompUnit → {Decl} {FuncDef} MainFuncDef // 1. existence of Decl 2. existence of FuncDef
Decl → ConstDecl | VarDecl // covers both kinds of declarations
ConstDecl → 'const' BType ConstDef { ',' ConstDef } ';' // 1. zero repetitions inside braces 2. multiple repetitions inside braces
BType → 'int'
ConstDef → Ident [ '[' ConstExp ']' ] '=' ConstInitVal // covers scalars and one-dimensional arrays
ConstInitVal → ConstExp | '{' [ ConstExp { ',' ConstExp } ] '}' // 1. constant expression initializer 2. 1D array initializer
VarDecl → [ 'static' ] BType VarDef { ',' VarDef } ';' // 1. zero repetitions inside braces 2. multiple repetitions inside braces
VarDef → Ident [ '[' ConstExp ']' ] | Ident [ '[' ConstExp ']' ] '=' InitVal // covers scalar and 1D array definitions
InitVal → Exp | '{' [ Exp { ',' Exp } ] '}' // 1. expression initializer 2. 1D array initializer
FuncDef → FuncType Ident '(' [FuncFParams] ')' Block // 1. no formal parameters 2. with formal parameters
MainFuncDef → 'int' 'main' '(' ')' Block // main function exists
FuncType → 'void' | 'int' // covers two function return types
FuncFParams → FuncFParam { ',' FuncFParam } // 1. zero repetitions inside braces 2. multiple repetitions inside braces
FuncFParam → BType Ident ['[' ']'] // 1. scalar variable 2. 1D array variable
Block → '{' { BlockItem } '}' // 1. zero repetitions inside braces 2. multiple repetitions inside braces
BlockItem → Decl | Stmt // covers two types of block items
Stmt → LVal '=' Exp ';' // all statement types shall be covered
| [Exp] ';' // two cases: Exp present or absent; for printf calls
| Block
| 'if' '(' Cond ')' Stmt [ 'else' Stmt ] // 1. with else 2. without else
| 'for' '(' [ForStmt] ';' [Cond] ';' [ForStmt] ')' Stmt // 1. no omitted parts, 1 case; 2. one omitted in ForStmt/Cond, 3 cases; 3. two omitted in ForStmt/Cond, 3 cases; 4. all omitted, 1 case
| 'break' ';'
| 'continue' ';'
| 'return' [Exp] ';' // 1. with Exp 2. without Exp
| 'printf' '(' StringConst {',' Exp} ')' ';' // 1. with Exp 2. without Exp
ForStmt → LVal '=' Exp { ',' LVal '=' Exp } // 1. zero repetitions inside braces 2. multiple repetitions inside braces
Exp → AddExp // existence only
Cond → LOrExp // existence only
LVal → Ident ['[' Exp ']'] // 1. ordinary variables/constants 2. one-dimensional arrays
PrimaryExp → '(' Exp ')' | LVal | Number
Number → IntConst // existence only
UnaryExp → PrimaryExp | Ident '(' [FuncRParams] ')' | UnaryOp UnaryExp // all three cases must be covered; function calls cover variants of FuncRParams
UnaryOp → '+' | '−' | '!' Note: '!' only appears in conditional expressions // all three must be covered
FuncRParams → Exp { ',' Exp } // 1. zero repetitions inside braces 2. multiple repetitions inside braces 3. Exp covers array passing and partial array passing
MulExp → UnaryExp | MulExp ('*' | '/' | '%') UnaryExp // 1.UnaryExp 2.* 3./ 4.% all must be covered
AddExp → MulExp | AddExp ('+' | '−') MulExp // 1.MulExp 2.+ must be covered 3.- must be covered
RelExp → AddExp | RelExp ('<' | '>' | '<=' | '>=') AddExp // 1.AddExp 2.< 3.> 4.<= 5.>= all must be covered
EqExp → RelExp | EqExp ('==' | '!=') RelExp // 1.RelExp 2.== 3.!= all must be covered
LAndExp → EqExp | LAndExp '&&' EqExp // 1.EqExp 2.&& all must be covered
LOrExp → LAndExp | LOrExp '||' LAndExp // 1.LAndExp 2.|| all must be covered
ConstExp → AddExp Note: Identifiers used must be constants // existence only
```

## 3.2 Supplementary Notes

### (1) Identifiers (`Ident`)

The specification for `Ident` in SysY (identifier):

```
identifier → identifier-nondigit
| identifier identifier-nondigit
| identifier digit
```

where `identifier-nondigit` is underscore or upper/lowercase letter; `digit` ranges from `0` to `9`.

Reference: ISO/IEC 9899 [http://www.open-std.org/jtc1/sc22/wg14/www/docs/n1124.pdf](http://www.open-std.org/jtc1/sc22/wg14/www/docs/n1124.pdf) page 51 for identifier rules, and rules for **identical identifiers**:

- Scopes of global variables/constants and local variables/constants may overlap; local declarations take precedence in overlapping regions.
- Local declarations with identical names cannot have overlapping scopes: no duplicate identifiers (constants/variables) inside one block.
- In different scopes, variable/constant names may reuse function names in SysY.
- Reserved keywords cannot be used as identifiers.

```
// Valid example
int main() {
	int a = 0;
	{
		int a = 1;
		printf("%d",a); // outputs 1
	}
	return 0;
}
```

```
// Invalid example
int main() {
	int a = 0;
	{
		int a = 1;
		int a = 2; // Invalid!
	}
	return 0;
}
```

### (2) Comments

SysY comment rules are identical to C:

- Single-line comment: starts with `//` and ends at newline (newline excluded).
- Multi-line comment: starts with `/*` and ends at the first occurrence of `*/` (the terminating `*/` is included).

Reference: ISO/IEC 9899 [http://www.open-std.org/jtc1/sc22/wg14/www/docs/n1124.pdf](http://www.open-std.org/jtc1/sc22/wg14/www/docs/n1124.pdf) page 66 for comment definition.

### (3) Numeric Constants

Numeric constants in SysY are integer constants `IntConst`, defined as (`integer-const`):

```
integer-const → decimal-const | 0
• decimal-const → nonzero-digit | decimal-const digit
• nonzero-digit: digits from 1 to 9
```

Reference: ISO/IEC 9899 [http://www.open-std.org/jtc1/sc22/wg14/www/docs/n1124.pdf](http://www.open-std.org/jtc1/sc22/wg14/www/docs/n1124.pdf) page 54 for integer constants; all suffixes are ignored.

### (4) String Constants

Definition of `<StringConst>` in SysY:

```
<FormatChar> → %d
<NormalChar> → ASCII characters with decimal codes 32, 33, 35–126; backslash (code 92) appears only as '\n'
<Char> → <FormatChar> | <NormalChar>
<StringConst> → '"' {<Char>} '"'
```

Only one escape sequence `\n` is allowed inside strings to represent a newline; no other escape sequences need to be handled.

# 4. Semantic Constraints

The set of programs accepted by the above grammar is a superset of valid SysY programs. The semantic constraints of SysY are given below.

## Runtime Library

1. **To reduce implementation complexity, `getint` and `printf` in all test programs are only used as runtime library calls and will not be defined as user variables or function identifiers.**
2. `printf` does not append a newline by default.
3. Similar to C `printf`, format specifiers are replaced by corresponding argument values; ordinary characters are printed verbatim.

## `static` Keyword

1. `static` modifies **static local variables** and never appears on global variable definitions.
2. If a `static` variable has an initializer, the initial value must be computable at compile time.
3. A `static` variable declared without an explicit initializer is zero-initialized by the compiler.
4. A `static` variable is initialized exactly once and retains its state across subsequent invocations of the enclosing function; it is not destroyed when the function exits, but its scope is limited to that function.

## Compilation Unit `CompUnit`

```
CompUnit → {Decl} {FuncDef} MainFuncDef
Decl → ConstDecl | VarDecl
```

1. Top-level variable/constant declarations (`Decl`) and function definitions (`FuncDef`) in one compilation unit cannot redefine the same `Ident`, even with different types.
2. The scope of top-level variables, constants and functions starts at their declaration and ends at the end of the source file.

## Constant Definition `ConstDef`

```
ConstDef → Ident [ '[' ConstExp ']' ] '=' ConstInitVal
```

1. `ConstDef` defines a symbolic constant. `Ident` is the constant identifier. The optional `[ConstExp]` after `Ident` and before `=` declares a one-dimensional array and its length. Constants must have initializers.
2. Without the array part, it declares a single scalar constant.
3. With the array part, it declares an array with semantics identical to C; indices start at `0`.
4. Each `ConstExp` specifying array length must evaluate to a **non-negative integer at compile time**.

## Variable Definition `VarDef`

```
VarDef → Ident [ '[' ConstExp ']' ] | Ident [ '[' ConstExp ']' ] '=' InitVal
```

1. Variable definitions are similar to constants, but variables may omit initializers; their runtime value is undefined in that case.

## Initializers `ConstInitVal` / `InitVal`

```
ConstInitVal → ConstExp | '{' [ ConstExp { ',' ConstExp } ] '}'
InitVal → Exp | '{' [ Exp { ',' Exp } ] '}' | StringConst
```

1. Constant initializers must be constant expressions `ConstExp`.
2. **Constants require initializers. Constant arrays may omit some element initializers; omitted elements are zero-filled by the compiler.**
3. Global variable initializers must be `ConstExp`. Local variable initializers are ordinary `Exp` and may reference previously declared variables.
4. For scalar constants or variables, the initializer must be a single expression (expressions include literals, variables, constants, etc.).
5. **Global variables without explicit initializers are zero-initialized; local variables are not.**

## Formal Parameters `FuncFParam` and Actual Parameters `FuncRParams`

```
FuncFParams → FuncFParam { ',' FuncFParam }
FuncRParams → Exp { ',' Exp }
```

1. `FuncFParam` defines one formal parameter. The optional `[]` marks an array parameter.
2. The syntax of actual arguments is `Exp`. Ordinary variables are passed by value. For array parameters, the formal parameter receives the address of the actual array and accesses elements indirectly via that address.
3. Ordinary constants may be passed as function arguments, but constant arrays cannot. Example: `const int arr[3] = {1,2,3}`; the constant array `arr` cannot be passed into a function.
4. Actual arguments must match formal parameters in type, see example below.

```
void f1(int x){
	return ;
}
void f2(int x[]){
	return ;
}
int main(){
	int x = 10;
	int t[5] = {1, 2, 3, 4, 5};
	f1(x); // valid
	f1(t[0]); // valid
	f1(t); // invalid
	f2(t); // valid
}
```

## Function Definition `FuncDef`

```
FuncDef → FuncType Ident '(' [FuncFParams] ')' Block
```

1. `FuncType` specifies return type. For `int`-returning functions, every control-flow branch must contain a `return` with an expression; branches without `return` yield undefined return values. For `void` functions, only `return` without an expression is allowed.
2. Semantics of `FuncFParams` are as described above.

## Block `Block`

1. A block introduces a scope; constants and variables declared inside live only within that block.
2. A block may redeclare names from outer scopes via `Decl` statements; inner declarations shadow outer ones from their definition until the end of the block.
3. For test simplicity, **all non-void functions in test cases end with an explicit `return` statement; missing `return` at function end is treated as an error.** Student-written test programs must follow this rule.
4. The `main` function must return constant `0`.

## Statements `Stmt`

1. `if` statements follow the nearest match rule (dangling-else rule).
2. A bare `Exp` can be a statement: the expression is evaluated and its result discarded.

## Lvalue `LVal`

1. `LVal` denotes an lvalue expression: a variable or array element.
2. For array access, the number of bracket subscripts must match the array dimension to select an element.
3. Scalar variables cannot have trailing subscript brackets.

## `Exp` and `Cond`

1. **`Exp` represents expressions of type `int` or `void`. `Cond` denotes a condition expression and is defined as `LOrExp`. The unary `!` may only appear in `Cond`, not in ordinary `Exp`.**
2. The identifier in an `LVal` must be defined before use in the current scope. The left-hand side of an assignment must be a variable, not a constant.
3. Function call syntax: `Ident ( FuncRParams )`. The number and types of actual arguments must exactly match the corresponding function definition.
4. Operator precedence and associativity follow C and are encoded in the grammar above.

## Unary Expression `UnaryExp`

1. Two identical consecutive unary operators are forbidden, e.g., `int a = ++-i;` is invalid, while `int a = +-+i;` is allowed.
2. Unary `!` may only appear inside conditional expressions.

## Constant Expression `ConstExp`

1. **`ConstExp` denotes an `int` expression.**
2. `ConstExp` must be evaluable at compile time. All identifiers inside a `ConstExp` must refer to constants, i.e., only literals, named constants with known values, and compile-time computable arithmetic expressions composed of them.

## Special Notes

1. For errors `i,j,k`, the "preceding nonterminal" refers to the nonterminal before `;`, `)`, `]` in grammar rules. The analyzer examines the last token of the token stream generated by this nonterminal, i.e., the token immediately before the expected `;`, `)`, or `]`.
2. No malicious newlines appear in any test case, including newlines inside character/string literals and function calls. A malicious newline refers to newlines that make error recovery difficult.
3. For other error types, report the line number of the first token where the error can be diagnosed. Example: missing return in non-void functions is diagnosed when reaching the closing `}` of the function block; report the line of `}`.
4. To avoid grammar ambiguities caused by test-case errors and prevent incorrect parse tree construction: **`for` statements contain no errors other than type `h`. Moreover, all errors that would prevent constructing a valid parse tree are absent.**
5. At most one error per source line.
6. **Functions and variables cannot share the same name in the same scope.**
7. If a function name is redefined, the compiler must still fully analyze the function body for other errors.
8. Two type-mismatch cases in function calls:
   - Passing an array to a scalar parameter.
   - Passing a scalar to an array parameter.
